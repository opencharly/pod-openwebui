# 2026.330.2029 — fix(openwebui): poll the web interface to 10m and persist the XDG cache home

## Summary

Two changes to the `openwebui` candy, both about the same measured behaviour: a cold Open WebUI start
is slow because it re-fetches its embedding model, and the readiness probe gave up before that budget.

**1. The readiness probe's window.** *"the Open WebUI web interface answers HTTP 200 on the published
port"* gave up after `eventually: 3m`. Measured on torn-down-and-re-created deployments:

- the probe expired at `attempts=81, elapsed=2m59.61s` while the server was healthy moments later;
- a cold container **re-fetches** the sentence-transformers embedding model (its cache lived in the
  container, not on a volume): **first `200` at 254 s**, `Fetching 30 files` still in the log past
  two minutes (filed as #36).

The window becomes `eventually: 10m`, `retry_interval: 5s` (per-attempt `timeout: 30s` unchanged). 5 m
would have passed the measured run by 46 s — too thin. 10 m stays a bounded poll, never a sleep.

**2. The cache that makes the window a fallback, not the fix.** The candy declared only the `data`
volume at `/opt/data`, so `huggingface_hub` resolved `HF_HOME` to `$XDG_CACHE_HOME/huggingface`
(default `~/.cache/huggingface`) **inside the container's writable layer**. A `cache` volume at
`~/.cache` now persists the XDG cache home, and a runtime check asserts the structure: the cache path
is a MOUNT POINT and the app's own resolver names a path under it.

The path is `~/.cache`, **not** `${HOME}/.cache`: a candy volume path is expanded by
`sdk/deploykit.expandVolumeHome`, which resolves `~/`, `~` and `$HOME` but not the braced `${HOME}`
form, and the first witness run proved it — the unexpanded `${HOME}` was rejected by podman (or
expanded by quadlet to the *host* home), and `hf-cache-on-the-volume` FAILED. The `~` spelling is what
every other candy uses and what the unit below shows. The diverging second expander is filed as
`sdk#647`.
