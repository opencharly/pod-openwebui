# 2026.319.0943 — feat(openwebui): use Qdrant as the RAG vector store via env_accept/secret_accept

## Summary

Make an Open WebUI deploy able to use **Qdrant** as its RAG vector store, through charly's
existing mechanisms only: the qdrant layer's `env_provide` (`QDRANT_URL`) reaches this candy's
`env_accept`, its `secret_require` key (`charly/api-key/qdrant`) reaches this candy's
`secret_accept`, and the entrypoint projects both onto the variables Open WebUI actually reads.

- `env_accept`: `QDRANT_URL` (the provider's name — provides are name-matched, so declaring
  `QDRANT_URI` here would inject nothing) plus the optional upstream pass-throughs
  `QDRANT_ON_DISK`, `QDRANT_COLLECTION_PREFIX`, `QDRANT_PREFER_GRPC`, `QDRANT_GRPC_PORT`,
  `ENABLE_QDRANT_MULTITENANCY_MODE`, `QDRANT_TIMEOUT`.
- `secret_accept`: `QDRANT_API_KEY` at `key: charly/api-key/qdrant` — the same credential the
  qdrant layer generates. Never an `env_provide`: that would write the key into the image's
  `ai.opencharly.env_provide` OCI label in cleartext.
- `openwebui-entrypoint`: one new block. With `QDRANT_URL` present it exports
  `VECTOR_DB=qdrant` and `QDRANT_URI="$QDRANT_URL"`; with the URL but no key it **fails loud**
  (an optional `secret_accept` that misses is silently omitted, and a keyless Qdrant only fails
  later as a 401 behind a 503); with neither it changes nothing, so upstream keeps Chroma.
- `pixi.toml`/`pixi.lock`: pin `qdrant-client==1.18.0`. Upstream declares it only under the
  `all` extra, and the vector factory builds the client while `routers/retrieval` is imported —
  without the package `VECTOR_DB=qdrant` stops the app from booting at all. `open-webui[all]` is
  deliberately NOT used (it also drags in playwright, colbert-ai, oracledb, azure-search,
  pymilvus, weaviate, pinecone).
- Three build-scope witnesses on the candy's own plan, same stub technique as the existing
  provider checks: wired, absent (Chroma default untouched), key-missing (exit 1).
- Skill: a "Vector store: Qdrant as the RAG backend" section on the candy skill, and the
  `openwebui-layer` skill's env/secret tables corrected — it listed `OPENROUTER_API_KEY`,
  `OLLAMA_API_KEY`, `OPENAI_API_KEY` under *env_accept* and `WEBUI_ADMIN_EMAIL` as an optional
  accepted var, while the manifest declares the keys `secret_accept` and the email `env_require`.

Follows the provider-block shape that #21 (TTS), #22 (STT) and #24 (ComfyUI) established.

## How tested

This repo is a candy repo with no in-repo `disposable: true` target, so the gate is
`charly box validate` + the org `charly/pr-validator`, with the candy's own build-scope checks
executed on a composed image and the changed runtime path exercised live on a disposable deploy
of that image.

```
$ charly -C <candy worktree> box validate
charly box validate: OK — checked 9 candies, 7 distros, 7 builders; 0 warnings, 0 errors

$ charly -C <distro worktree> box build owui-qdrant-proof           # BUILD_RC=0
$ charly -C <distro worktree> check box owui-qdrant-proof
44 steps: 30 passed, 0 failed, 14 skipped

$ charly remove owui-qdrant-proof && charly config ... && charly start ...
$ charly -C <distro worktree> check live owui-qdrant-proof
44 steps: 41 passed, 0 failed, 3 skipped
   PASS entrypoint-qdrant-wired        exit=0
   PASS entrypoint-qdrant-absent       exit=0
   PASS entrypoint-qdrant-key-missing  exit=1
   PASS proof-image-qdrant-client      exit=0
   PASS proof-same-deploy-provide      exit=0   (same-deploy provide resolves to localhost)
   PASS proof-local-write              exit=0   (collection written with the injected credential)
```

The composition is a disposable `owui-qdrant-proof` deploy (distro-fedora, session worktree)
composing this candy with `layer-qdrant:v2026.314.0709`. Fidelity to this branch, mechanically:

- `openwebui-entrypoint`, `pixi.toml`, `pixi.lock` — `sha256sum` IDENTICAL to this head.
- `charly.yml` — identical candy body; the scaffold copy differs only by the top-level node name
  (`openwebui:` → `owui-qdrant-proof:`) and by omitting the trailing `openwebui-skill:` node,
  which the build does not need. Verified with
  `diff <(sed '1s/^owui-qdrant-proof:/openwebui:/' <scaffold>) <head>` — the only hunk is the
  removed skill node.

Also measured while exercising the pair: `charly qdrant collections list` (host-side, R5/R3
parity) lists the collection the consumer wrote, and the service log shows
`openwebui-entrypoint: Qdrant vector store at …`.

## Change classification

Additive. A deployment that provides neither `QDRANT_URL` nor `QDRANT_API_KEY` behaves exactly
as before (upstream Chroma) — proved by the `entrypoint-qdrant-absent` witness. Rollback is
dropping the two entries and the entrypoint block; no Open WebUI data migration is involved
(the vectors live in Qdrant).
