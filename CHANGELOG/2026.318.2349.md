# 2026.318.2349 — feat(openwebui): declare the ComfyUI image-generation contract (a URL instead of a shell incantation)

## Summary

The ComfyUI ↔ Open WebUI integration **works** — proven end to end on real GPU pods (Open WebUI
`POST /api/v1/images/generations` → 200 → a 512×512 PNG, with ComfyUI's `/history` recording the same prompt).
But it worked only for someone who knows the incantation; every env var was passed by hand, and this candy
mentioned neither `comfyui` nor `IMAGE_GENERATION`:

```
charly config openwebui -i lab -e COMFYUI_BASE_URL=http://charly-comfyui-lab:8188 \
  -e IMAGE_GENERATION_ENGINE=comfyui -e ENABLE_IMAGE_GENERATION=true \
  -e COMFYUI_WORKFLOW_NODES='[{"type":"prompt","node_ids":["6"]},…]'
```

A feature that lives in an operator's shell history is folklore, not a product. Refs #23.

**What this changes:**

1. **`IMAGE_GENERATION_ENGINE: comfyui`** is now a candy-level `env:` constant — the engine is a property of the
   wiring, not a per-deploy choice.
2. **`env_accept`** declares the FOUR inputs that *do* vary:
   - `COMFYUI_BASE_URL` — a ComfyUI deploy can inject it through `env_provide`, so the common case becomes
     "point this deploy at that one";
   - `ENABLE_IMAGE_GENERATION` — generation stays OFF until an operator turns it on, so a deploy with no ComfyUI
     behind it never advertises a feature whose server is absent;
   - `COMFYUI_WORKFLOW_NODES` — documented as optional (Open Web UI's own default workflow applies when unset);
   - `IMAGE_GENERATION_ENGINE` — the engine default is baked into the IMAGE, so this row exists for deploys against
     an image built BEFORE the contract, which carries no default at all (see the caveat below).
3. **The layer skill** gains an *Image generation (ComfyUI)* section: the minimal wiring, the shared-pod-network
   requirement that makes `http://<comfyui-deploy>:8188` resolve, and where a round-trip is verified (Open
   Web UI's own data volume vs ComfyUI's `/history`).

**A measured caveat, documented rather than hidden — and the design changed because of it.** `env:` defaults are
IMAGE-level: an image built BEFORE this change carries no `IMAGE_GENERATION_ENGINE`. My first cut made the engine
an `env:` constant ONLY, which left a deploy against a pre-existing image with no way to supply it — the review
caught that the skill's "minimal wiring" was therefore wrong for those images. `IMAGE_GENERATION_ENGINE` is now
**also an `env_accept` row** (the schema accepts the name in both places; `box validate` rc=0), so an old image
has an escape hatch, and the skill states the caveat *before* the wiring block.

Measured on this host with the new candy and the existing image:

```
$ … charly config openwebui -i l4 -e COMFYUI_BASE_URL=http://charly-comfyui-lab:8188 -e ENABLE_IMAGE_GENERATION=true -p 18090:8080
$ grep -oE '(IMAGE_GENERATION_ENGINE|ENABLE_IMAGE_GENERATION|COMFYUI_BASE_URL)=[^ "]*' …/charly-openwebui-l4.container
COMFYUI_BASE_URL=http://charly-comfyui-lab:8188
ENABLE_IMAGE_GENERATION=true
```

The engine default is absent because it lives in the image, not the deploy — which is exactly why the skill
prose says so instead of promising "a URL is all you need" for images that predate this contract.

**What this PR does not prove, and where that lives.** The end-to-end generation path is a runtime behaviour of
the composed image; its gate is the integration bed tracked with the ComfyUI shipping legs, not a schema check
in this repo. This PR's own scope is the contract's declaration, and `box validate` plus the emitted quadlet
above are its artifacts.
